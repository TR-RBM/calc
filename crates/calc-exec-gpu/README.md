# calc-exec-gpu

## What it does

The GPU backend, without a hardware device. Nothing in this crate is registered in a shipped build.

- `Kernel` is the program format. A map pass holds statements in single assignment order: an input channel, a constant, an operation on earlier locals, a comparison, `And`, `Or`, `Not` or `Select`, and the locals it writes out. A kernel has five buffers: the input values of all channels in one flat buffer (channel times batch length plus element), the constants, the outputs in the same flat layout, the reduce target, and the index triples of a reduce stage. Every constant of a plan is read from the constants buffer, never written as a literal, so no shader compiler sees an operation on constants.
- A map pass may hold iterations: an `Iterate` statement names a `KernelIteration` with initial locals, a body of statements that read `State` slots and `Outer` locals, one `next` body local per slot, a truth `exit` and a `maximum_count`. `IterationState` statements read the final state. Each element tests the exit before every step and stops there.
- `validate` checks a kernel before it is compiled: every buffer exists and has the kind its use needs, no pass reads and writes the same buffer, every input channel and constant index is in range, every statement uses only earlier locals of the right kind, and there is at least one result, each a value. For iterations it also checks scope (no input or iteration inside a body, no state or outer outside it), slot counts and kinds, the exit kind and every reference, with `StatementError` and `IterationError` naming the failure. So no result can depend on the order of invocations inside a dispatch.
- `lower_plan` turns an `F32` plan into a kernel. `F64` plans and approximate operations are unsupported, as `GpuBackend` also declares in its capabilities. Plan iterations become kernel iterations.
- `halving_stages(length)` builds the index triples of the `Halving` tree, one list per stage. A triple is (left, right, result), and a right index of `CARRY` copies the left value into the next stage. The number of stages is the tree depth.
- `emit_map` and `emit_reduce` write the WGSL text of a kernel's two passes: a prelude with bit-exact helpers, the storage and uniform bindings, and one compute entry point each, `map_main` and `reduce_main`, with a workgroup size of 64 and a two-dimensional invocation index for more than 65 535 workgroups. `loop_text` writes an iteration as `var` state, one `for` loop with the fixed maximum count, the body statements, a `break` when the exit holds and the state updates, so the shader has the same length for any count. `statement_text` writes one statement per kernel expression. The text never depends on the compiler's treatment of special values: negation, absolute value and `CopySign` are bit operations on `bitcast<u32>`; NaN is tested on the bits; every comparison is false when an operand is NaN, except `!=`, which is true; and `Min` and `Max` are the IEEE `minimum` and `maximum` written with `select`. Every emitted text passes `check_shader_text`, which rejects the type `f16` and `enable f16;`.
- `GpuDevice` is the device trait: create, write and read buffers, compile a kernel, and dispatch its map or reduce pass over a list of buffers. A device is a cheap `Clone` handle, so each prepared plan holds its own.
- `SoftwareDevice` implements `GpuDevice` on the CPU with `f32` arithmetic and the IEEE `minimum` and `maximum` of `calc-numbers`. It runs the invocations of every dispatch in an order permuted by the seed it was built with, and applies reduce writes only after all reads. `SoftwareFault` injects out of memory, a lost device and a rejected buffer.
- `GpuBackend` implements `Backend` over any `GpuDevice`: `F32` only, the correctly rounded operations except `MulAdd`, which WGSL cannot guarantee to fuse, iterations up to 65 536 steps, the escape-time cap, and transfer costs. A run writes the flat inputs and the constants, dispatches the map pass, and then reads the outputs; reduces a `LeftFold` on the host after reading the map output; or runs one reduce dispatch per `Halving` stage, swapping source and target between stages, and reads the single result. Its `RunReport` counts every write and read as one transfer and every entry moved. Device failures become `PrepareError` or `RunError` variants, and nothing falls back.

## How to test

`cargo test -p calc-exec-gpu`

Each statement kind and the loop have a test of their expected WGSL text, and the shader text check has tests for `enable f16;`, the `f16` type and an identifier that merely contains `f16`. Each correctly rounded operation and each reduce operation and shape at the lengths of `calc-conformance` runs through `check_bitwise` against `calc-exec-cpu` on `SoftwareDevice` with three seeds, one test per operation, plus the contraction case. The iteration cases run through `check_unrolled`, and both escape-time forms through `check_equivalent` against the unrolled escape-time circuit on `calc-exec-cpu`, on three seeds. Removing the exit test from the software loop makes six tests fail. The validator has one test per rule. Transfer counts are asserted for a map run with and without constants, a `Halving` run of 1025 elements and a `LeftFold` run. Every device failure is produced by fault injection. Moving the extra element of an odd split to the left half, and dropping the buffer swap between reduce stages, each make conformance tests fail.
