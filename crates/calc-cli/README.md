# calc-cli

## What it does

The command line frontend, the `calc` binary.

- `calc <expression>` enters the expression into a new session, evaluates it and prints the line: its label and input, then value, uncertainty, kind, rounding error, method, backend and dependencies, with the labels aligned to the longest label in the active locale. Value, uncertainty and rounding bound are printed in the displayed unit, so `calc "5 km"` prints `5 km`, while `--json` keeps the coherent unit. A value that is exact and not written as a finite decimal carries an approximate reading beside it, as `1250/9 ≈ 138.9 m`: four significant digits from the exact value, rounded as schools round. An integer, a decimal, a machine value and a measured value get none, the reading is never repeated in a `--digits` or `--enclose` view, and `--json` never carries one.
- `calc <file.calc>` opens the session file, prints every line in stack order and then the status row: replay state, number of results, running and differing lines, locale, precision and backend. Opening does not recompute. A line names its recognition in a `concept` row as one of three answers: the concepts it matched, that none in the concept set matches, or why recognition could not run. A record whose recognition never ran has no row. An offer the recognizer cut short ends with `and more`, and a search cut short before any concept matched says that rather than that nothing matched. A match whose concept this version does not hold is counted rather than named or dropped, as `and one concept this version does not know`, and the row is one list whose last part takes the `and`; where the concept set could not be loaded at all nothing is counted and the row says that instead, since this version may hold every one of those concepts and simply have no content in front of it. A concept is named in the display locale, as `calc concept` names it, never by its identifier; an identifier stands there only when the concept set cannot name it, since a match that cannot be named is still a match and dropping it would lose what the record says.
- `--json` prints each line as the session file's line object in canonical form instead of text. The status row is not printed with `--json`. A parse error of the entered text is printed on standard error as a typed error instead of prose: `recognised_attempt` with its attempt, column, replacement and corrected text; `ambiguous_application` with function, written, column, narrow and wide; `ambiguous_temperature_sign` with sign, written, column, difference and reading; and `parse_error` with the kind and the column for everything else. The code and the data members are those a stored line of the same text carries when a session is opened, so a program reads one answer either way. The exit code is unchanged.
- `--units <system>`, `--unit <kind>=<unit>` and `--coherent-units` choose the unit a value is shown in, for this run only. `--units` names a system the content ships, `si` or `us-customary`; `--unit` sets one quantity kind and may be given once per kind; `--coherent-units` shows every value in its coherent unit and cannot be given beside either of the others. They are this run's display choice: nothing is written to the session file, no value and no record changes, and `--json` is the same bytes with them and without, because it is in coherent units. In the order that decides the displayed unit they stand below a unit written in the expression, which always wins, and below a session's saved override, so opening a session that carries one shows the override and not the option. An unknown system, an unknown kind, an entry that is not `<kind>=<unit>`, the same kind twice, or `--coherent-units` beside a chosen unit is a usage error with exit code 2.
- `calc <input> --inspect` shows the Inspect instrument of one line: the record as the default output prints it, and beside it whether the recognizer tried every concept, was cut short, or wrote a file that does not say. It is the form that shows one line of a session file, `calc <file.calc> <line> --inspect`, which otherwise needs a view flag. Which instruments a line has comes from `calc-app`'s `applying_instruments`, so the terminal and the cockpit offer the same ones: a naming is refused, because Inspect exists for a naming only where the stack shortened it and the terminal shortens nothing, and the refusal names the forms that line does have, or says it has no other. Exit code 1, since the command line was understood and the line has no such form. `--inspect` beside `--digits`, `--enclose` or `--working` is a usage error: a line is shown in one form at a time.
- `--locale <tag>` chooses the language. Without it the locale comes from `LC_ALL`, `LC_MESSAGES` and `LANG` through `calc-i18n`. An invalid tag is a usage error reported in English.
- The GPU backend is probed late and only when a plan selects it. An exact run never asks for it at all: the session asks for a further backend the first time machine evaluation is reached, and `calc plot` and `calc read` ask before sampling, since sampling is always a machine plan, but that ask costs nothing on its own. The backend that stands for the GPU answers its capabilities from the committed cost parameters, so no run enumerates an adapter to find out whether one exists. The device is created, and the adapter probe run, by the first plan that selects it: the probe's 0.686 s, measured on an RTX adapter, is paid by a plan large enough to have chosen a device, and never by a plan that only asked whether one was there. The result is not remembered across starts, so a long-running process pays it once and a repeated one-shot `calc` pays it again whenever a plan selects the GPU; a stored result would need an argument about how it is invalidated, never a quiet cache. A refusal is printed as one line on standard error where a plan selected the GPU and could not have it, including the ordinary case of no adapter; it is not an error and the exit code is unchanged. `calc solve` keeps the CPU backends, because its evaluation context is built before anything is known about the plans.
- `calc <input> --how-it-ran` says how the backend ran each operation of the line, in the words the cockpit's block uses: one row per execution mode with its operations, a row for the operations the backend does not offer, and the sentence saying what a native mode does and does not claim. A line evaluated exactly says that no backend ran an operation, and a backend that reports no modes says it ran every operation one way. Rows wrap within 80 columns, between operations and never inside a name.
- `calc <expression> --working` and `calc <file.calc> <line> --working [<path>]` show how the result was reached: one row per step, the operation with its operands and its result, and for a subexpression whose steps were not expanded a row saying how many further steps there are and one `--working <path>` row per path, written as the flag takes it so it can be copied. `--json` prints the outcome with its steps, `further_steps` and `further_paths`. The view is never on by default and changes no value.
- `--help` prints the manual page: the name and what calc is for, a synopsis grouping the subcommands and the modes of the main command, a description of each subcommand, every option the binary accepts, the meaning of each exit code, and examples last. A usage mistake prints the short synopsis instead, on standard error, with exit code 2. Every line of the page is wrapped by the CLI within 80 columns, with continuation lines indented to the column they continue, and a test fails on any line wider than that in either locale.
- `calc concept <identifier> [--lens <area>]` prints a concept from calc-app's concept command: its identifier and name, its statement and whatever of intuition, examples and misconception the content has in the display locale, the lens asked for, the lenses that have something to show, and its prerequisites, sources and exercises. A lens with nothing to show is not an error: the concept is printed and the row says that lens has nothing yet. An unknown identifier is a failure with the typed `unknown_concept` words and exit code 1. `--json` prints the outcome with identifiers and message keys and no rendered prose of ours; the concept's own text is content and is carried in the locale it is written in, which the `locale` member names.
- `calc help language` prints the language reference: every group with its entries, each entry's name and meaning in the display locale, its spellings as mode, pattern and example, its precedence and its argument counts, then the precedence table, the unit table and the decimal prefixes. `--locale <tag>` chooses the language. `calc help language --json` prints the typed reference instead, with the message key of every heading, name and meaning and no rendered words, so a program gets the same bytes in every locale. The JSON carries each unit's dimension exponents and exact scale factor, which the text rows leave out.
- `calc solve --json` reads one solve request from standard input, and `calc solve --json --request <json>` takes it as an argument. The answer is printed as canonical JSON with the keys of the solve request and answer, without prose. The exit code: 0 for `ways`, `front` and `solved`, 3 for `invalid_request` and 4 for `not_reached`, which is an answer and not a mistake. A usage mistake exits with 2, and unreadable input or an internal failure with 1, printing no answer and writing a typed error `{"code", "data"}` as JSON on standard error. The prose form of the answer is not there yet, so `calc solve` without `--json` is such an error. A request with phase `reachable` and no `wanted` is answered with the reachable listing and exit code 0.
- `calc <expression> --digits <n>` and `--enclose <n>` evaluate the expression and show the digits or enclosure view of its line instead of the record: decimal places, whether the digits are of the exact or the machine value, the truncated value, the remainder and the expansion, or the significant digits, lower and upper bound, width and whether the precision was reached. `calc <file.calc> <line> --digits <n>` and `--enclose <n>` show the view of a line of a session file. With `--json` the outcome is one JSON object with the members of that view. A view that does not apply or asks above its limit is an error on standard error with exit code 1.
- `calc read <file.calc> <line> --at <coordinates>` reads the line's picture at typed exact coordinates, one per axis, comma separated. It plots into slot 0 with the same `--view`, `--param` and `--size` options, waits for the bounds, and reads from the scene it drew. `--layer <index>` chooses the layer, the first by default. Without `--commit` it prints the record of the reading, as a line's record is printed, and changes nothing. With `--commit` it appends the call of the function at those coordinates as a new line, prints it as entering a line does, and writes the session file back. With `--json` the reading is printed in the session file's record form, and a committed reading in the session file line form.
- `calc plot <expression> --output <path>` and `calc plot <file.calc> <line> --output <path>` draw the line's picture into a PNG file. `--view <lower>..<upper> [unit]` sets the axes in scene order with exact bounds and an optional display unit, and axes without it keep the stored or default view. `--param <name>=<value>` gives a free variable an exact value. `--size <width>x<height>` sets the image size in pixels, default 800x600. The plot area comes from `calc-render`'s layout before sampling, its pixel counts are the divisions, the invocation is one picture slot, the CLI waits for the bounds, and the image is drawn with the light theme and written by the binary. `--limit fixed:<iterations>` or `--limit following:<base>,<per halving>,<cap>` sets the iteration limit of an escape-time line: whole numbers, `iterations` and `cap` at most 65536, the option given at most once, and only for an escape-time line, which is entered as the text `escape_time {...}` like any other expression. Without `--json` it prints the path and size and a line for each precision limit that applies; with `--json` it prints the path, the size, the view states and the precision limit of each layer. With `--settle` the view as drawn and the parameters are kept in the session file, which is written back to its path.
- `calc - --machine-line <line> <f64 or f32>` reads a session from standard input, adds the machine evaluation line and writes the saved session to standard output, with the same typed errors as the commands below, plus `invalid_machine_format` and `machine_line_not_applicable`.
- `calc - --solve <json>` reads a session from standard input, adds the solve line (`enter-solve`) and writes the saved session to standard output. `calc - --choose-wanted <line> <role>` does the same with `choose-wanted`, which turns a reachable line into a way search with the program default criterion and cap 5. Errors are typed JSON on standard error: exit code 3 for an invalid request, 1 for anything else. A session path instead of `-` is the typed error `saving_not_supported`, because `calc-app` cannot write session files yet.

Outside `calc solve`, the exit code is 0 on success, 1 when a line failed, the input does not parse or the file cannot be read, and 2 on a usage error. Errors go to standard error.

Every text the binary prints is a `calc-i18n` message rendered to `Localized`, and the output writer accepts only `Localized` text or the canonical JSON bytes from `calc-app`. The crate denies `clippy::print_stdout` and `clippy::print_stderr`. Error mapping, value text and the record summary live in `calc-app`, so the cockpit shows the same.

`calc --complete -- <word>...` answers a shell's completion: it prints what may follow the words, one candidate per line with its localized description after a tab, and exits 5 where file names fit as well. Each parser keeps its options in one table, `OPTIONS`, which refuses any option not in it and which `completion.rs` reads, so an option added to a parser is offered in both shells without a second edit. `completion/calc.bash` and `completion/calc.fish` are the two shell files that call it.

`main` reads the arguments, the locale variables and the file, and passes them to `run` with the system clock, so `run` is tested without a process, a file or a clock.

A line whose value is not a number does not let `calc` exit 0: a NaN in a result, in either part of a complex value or anywhere in an array, is nothing the run computed, so the exit code says the run did not carry the command out. An infinity is a value and exits 0, because the record states it with no error and an exit code that said otherwise would contradict the line it printed.

`calc --ode <system> --initial <values> --at <times>` encloses the solution of an initial value problem and prints, per time, each component between two decimals with its interval bound, then over the whole run each component's step bound and the method. The three options come together; a missing one is a usage error (exit 2). A problem that cannot be read or whose units do not fit exits 3; one the method cannot enclose, a blow-up or the step limit, exits 4, and the refusal at the step limit names the time scale of the last step.

## How to test

`cargo test -p calc-cli`

The tests in `tests/completion.rs` run `--complete` on the first word, a plot's options, the locales, a concept identifier and a German description; the unit tests in `completion.rs` check that every option in each parser's table is accepted by that parser.

The tests in `tests/units.rs` run the three unit options: a system and a per-kind unit each decide the unit a speed is shown in, `--coherent-units` gives the coherent one, a session's saved override wins over `--unit`, the JSON is the same bytes with the options and without, and each usage mistake exits 2 with its own sentence, one of them in German. The tests in `tests/reachable.rs` run two reachable requests, one with obtainable marks, check that the same request gives the same bytes, and run `--solve` and `--choose-wanted` through standard input. The tests in `tests/solve.rs` run `calc solve` on a ways request, an evaluated request and a not-reached request, and check the exit codes, the typed errors, and that the same ways request gives the same bytes through the argument and standard input. The tests in `tests/evaluate.rs` run the built binary on three expressions and compare its output, and check the JSON form and a parse error on standard error. The tests in `tests/plot_images.rs` run the binary on a curve, a grid, a complex grid, a curve over an axis in seconds and a function head with a parameter, and compare each PNG with the golden beside them; the last two are the external tests' own invocations, `calc plot "x * 1 m/s" --view 0..2 s`, whose axes read `time in s` and `length in m`, the quantity each dimension determines, and `calc plot "psi(x) = sqrt(2)*sin(n*pi*x)" --param n=3`, and a sixth, the picture run's break-even curve, which carries no units and keeps the names it had.
