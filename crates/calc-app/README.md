# calc-app

## What it does

The application layer shared by both frontends: sessions, commands, backend registration, and the mapping from core errors to messages.

So far it holds `ResultRecord`, the record of one result as the session file defines it. It combines the `ComputedResult` of `calc-core` with what only this layer knows: the backend use from selection in `calc-exec`, the lines the result depends on, the time the evaluation finished, its duration and the Calculator version that produced it.

`LineId` is the number of a line, starting at 1, printed as `r` and the number. Dependencies keep the order of first use and hold each line once. `UtcTimestamp` counts milliseconds since the Unix epoch, which is the resolution of the session file, so a record read back from a file equals the record that was saved. `CalculatorVersion::current` is the version of this crate.

`BackendUse.skipped` holds `SkippedBackendUse` values: the backend and the cause as the session file names it (`unsupported_domain`, `unsupported_operation`, `batch_too_long`), plus `PrepareFailed`, which the file format has no name for.

`Session` is one session: the settings, the lines in stack order, the expression pool and the registered backends. `registered_backends` returns the backends `calc-app` registers: the CPU backend, which receives a `SharedParallelism` of `ScopedThreadParallelism::available()`, and on x86-64 the SIMD backend. `ScopedThreadParallelism` is the native parallelism of the platform boundary: it runs the tasks on at most its worker count of `std::thread::scope` threads and returns when all have finished, and it is the only place below the frontends that starts threads for a backend.

- `enter` parses one statement of the input language and adds a line with the next label `r<n>`. A naming statement binds the name. `edit` replaces the text of a line and keeps its label, and its name unless the new text names it differently. Both fail without changing the session on a parse error, an existing name, a reference cycle, or a rename of a line that other lines use.
- A line refers to other lines by name or by label. Its dependencies are those lines in order of first use. A name that no line has makes the line fail with `undefined_name`, and the line is computed again when a line with that name is entered.
- Evaluation substitutes each referenced line by its own expression, with its references substituted in turn, and evaluates the result. Evaluating the whole expression, not stored values, keeps exact values exact and makes the rounding bound cover the whole chain.
- `edit` and `set_precision` recompute the changed lines and every line that depends on them, in dependency order with ties broken by stack order, and return the recomputed lines in that order.
- Every line is evaluated exactly first, and an exact rational result is kept under every precision setting so `0.1 + 0.2` is `3/10` under `f64` too. With `f64` or `f32` a line goes to the registered backends, in that plan domain, only when exact evaluation meets a machine operand, an expression it does not support, or an algebraic or symbolic result, which `ResultValue` cannot hold yet. An exact failure such as a division by zero is not retried in machine arithmetic. With `exact` such lines fail. A function definition fails with `function_definition_not_evaluated`. A failed line stores a typed error with a code and data, never text. A line whose dependency failed fails with `dependency_failed`.
- An exact result that is a rational times an integer power of pi, such as `pi/6`, `pi^2/6`, `1/pi` or `30 deg`, is kept exact under every precision setting as an expression value printed as `pi / 6`, `pi^2 / 6` or `1 / pi`, kind `symbolic`, with no rounding error. Only machine operands, other algebraic or symbolic results and unsupported nodes go to the plan domain, so `sin(1)` still evaluates in `f64`. `displayed_line_summary` converts such a value exactly when its displayed unit cancels pi, so `30 deg` prints as the exact integer 30 in degrees and `1 deg^2` as 1 in square degrees, while the kind stays `symbolic` as in the record and Inspect. A line such as `30 deg` that an earlier build stored as a machine float now replays to this exact value, so replay reports it as differing; that difference comes from the corrected rule, not from a fault.
- The clock comes from the `Clock` trait of the platform boundary. `SystemClock` is the native clock. `FixedClock` always reads one UTC time and advances its monotonic reading by a fixed step per reading, for reproducible records in tests and offscreen frames.

`save_to_bytes` writes the session in the canonical form of format version 7, which keeps everything of versions 2 to 6. A record carries `sources`, sorted without duplicates. A solve line's outcome is `Outcome::Answer` with the solve answer: the file status `ways` for an answer with status `ways` or `front`, `not_reached` and `solved`, derived from the answer so they cannot disagree. A version 1 file is converted on load by `convert_version_1`, which gives every record an empty `sources` list and rejects a solve outcome, then by `convert_version_2`, which gives every line `picture` and `reading` as `null`, and then by `convert_version_3`, which gives every `missing_any_of` entry of a not-reached answer `derivation` and `conditions` as `null`, keeping its stored `rule`, and its `bounds` `from` as `null`. These `null` members mean not recorded. `convert_version_4` then gives `settings` the member `units` as `null`, and `convert_version_5` gives every axis of a `picture` view and of a `reading` view the member `unit` as `null`. `convert_version_6` gives every stored condition of an answer's ways, entries and further inputs the member `parameters` as `null`, because a conversion reads no content. Saving writes version 7. An axis `unit` is `null` for the coherent unit, `{"unit": text}` for a unit, or `{"scale": "celsius"}` or `{"scale": "fahrenheit"}`, and the axis bounds and reading coordinates are in it (`AxisDisplayUnit`). The reader checks this structure and keeps a unit it cannot resolve. `settings.units` is `null` or the session's unit override: a unit system identifier or `null`, and `{kind, unit}` pairs sorted by kind without a repeated kind. The reader rejects an override with no system and no pairs, and keeps a system, kind or unit it cannot resolve, so saving does not lose it. `Session::unit_override` gives it; a new session has none. A not-reached entry carries the rule, the staged derivation, the rules between and the conditions of every rule with their three-valued `holds`, and `bounds.from` names the bounds each end came from. A line's `picture` holds the settled view states, with axis ranges and an optional camera, and the free parameter values. Its `reading` holds the source line, the view, the divisions and the snapped coordinates, all exact numbers. The reader rejects a reading whose source is a missing line or whose divisions or coordinates do not match its view's axes, a machine number in either member, and a repeated parameter name. Matching a picture against the line's scene happens when it is plotted, because the line alone does not fix its scene. `open_from_bytes` reads it strictly: it rejects a duplicate, missing or unknown member, a value outside the allowed set, a decimal that does not match its bits, a newer version, an answer whose status contradicts the line status, a `solved` answer without a record or a `ways` answer with one, a tie-break other than the one the solve request defines, a rank or layer that does not fit the combine, a truncation flag without its cause, a score of the wrong type, unsorted inputs or sources, a duplicate line id or name, a line number not below `next_line_number`, a name that differs from the naming statement of the input, a dependency on a missing line and a dependency cycle. Each error names the JSON path. Opening does not recompute. Saving a loaded session gives the same bytes, and a loaded session gives the same lines.

`Session::identifies_number` and `LineSummary::identifies_number` say whether a line's input identifies its number: the line is not a function definition and its expression refers to no name, line label or function: neither one a line defines nor a free name. Built-in constants and functions do not count. A solve line never identifies a number.

`display_unit_text` turns a unit in the canonical text of a record or answer, such as `m*s^-2`, into its display form for frontends: display symbols such as `°C`, superscript exponents, `·` between factors and `/` before negative exponents when a positive one exists. Text that is not a unit is returned unchanged.

`line_json` writes one line object in the canonical session file form followed by a line end, as the CLI prints it with `--json`.

`line_summary` and `status` give what both frontends show for a line and for the session as typed data, so a frontend can pick sign, kind bar and colour without matching words: the value text, unit, kind, uncertainty with its coverage factor, rounding error, method, backend and dependencies of a result, the message of a failed line (a solve line shows as not evaluated, because neither frontend shows its states yet), and the replay state, counts, precision and backend of the session. `kind_message`, `rounding_message`, `replay_state_message`, `precision_message`, `preference_message` and `backend_message` give the words for them at the frontend's edge. A summary line states what happened and never names an absence: `record_kind_message` names the width of a machine float, `method_message` gives every method identifier its own words and an unknown one through a message carrying it, `propagation_message` says how an uncertainty was propagated, `rounding_message` has no row for an exact value, and a line without a backend has no backend row. A solve line is summarised by what it found (`solve_line_message`). A measured value is evaluated at its central value and gets its propagated standard uncertainty from `calc-core`. A line's exact rational value is written in the form decided from its expanded expression (`Session::rational_form_of`, computed by `calc-core`'s `rational_form` when the line is evaluated and again when a session is opened, from the central expression of a measured line): a decimal when the expression has a decimal literal or `exact` and only operations that keep a terminating decimal terminating, a fraction otherwise. `value_text_in` writes a value in that form; a record inside a solve answer has no written expression of its own and takes the fraction form. `value_text`, used for data that is not a result value, prints a rational as a decimal when the decimal is finite and as a fraction otherwise. A machine number is written as its shortest decimal, in scientific form below 1e-5 and from 1e16. The frontends lay these out and compute nothing.

`messages` maps every error to a `calc-i18n` message: the stored diagnostic codes of a failed line, session errors, parse errors with their column counted in characters from 1, load and save errors of the session file, and the precision and backend settings. A diagnostic code without its own message becomes `error-internal` with the code. An evaluation error that names a part of the expression stores that part as `reading`, an `expression` value printed by `calc-syntax`, with a power in an exponent written in parentheses such as `10^(100^10)`, and next to it the limit, the argument or the estimated digit count as integer values. A result-size error on the whole expression is `result_too_large`, and one on a part of it is `intermediate_step_too_large`. A message shows a reading longer than 80 characters by its first and last 30 characters around an ellipsis, and an argument longer than 40 digits by its digit count. `values_equal` compares two values as replay does: machine values by their bits with every NaN equal, exact values by their digits, and expression values by parsing both into one pool.

Given and wanted. `parse_request` reads a solve request, fills every default, and rejects a structural fault with its error code and JSON path. `SolveRequest::line_text` writes `solve ` and the request as one-line JSON with every member, so a solve line never relies on a default. The engine loads the concept set of `calc-concepts` once per process, resolves the object kind, the wanted role and the marked roles, converts given values and uncertainties to coherent units with a dimension check, and runs the `calc-core` search. Phase `ways` ranks the listed ways by the criterion. Phase `evaluate` scores the ways whose inputs all have values, decides their conditions, and evaluates each way whose conditions all hold into a record in the wanted role's coherent unit, with the propagated standard uncertainty, the rule's sources and the `Rests on` blocks of its concepts as corpus references. A request that reaches nothing gives the smallest further input sets and the bounds that follow from the given values.

`solve` answers a request without a session and returns its status and canonical JSON. `Session::enter_solve` adds a solve line, and `mark`, `set_given`, `set_criterion`, `set_cap` and `find_ways` rewrite the request in the line's input text and recompute the line. An invalid request fails with `SessionError::InvalidRequest` and changes nothing. Formula and condition text has two forms.
- **Program form:** stored and written to JSON. The condition `text` is the way's body printed in ASCII over its own parameter names, and `parameters` lists `{name, role}` in parameter order with the roles of the rule, as in `r > 0 and t > 0 and t < 2 * pi` with `r` for `circle.radius` and `t` for `circle.central-angle`.
- **Person form:** never stored. `SolveVocabulary::person_condition_text` and `person_formula_text` print it in the Unicode mode of the input language with each parameter written as the curriculum's symbol for its role, from a symbol map the caller passes, or otherwise its running name. So a formula reads `U = 2 · π · r` with symbols and `chord = radius · √(2 - 2 · cos(central angle))` without. `person_text` does the same for any name function. A name of several words is written in parentheses where its parameter is the base or exponent of a power, or the operand of a unary minus, factorial or square root, so `a^2` over side a reads `(side a)²`. Quantities, arrays and binders are copied through, so a condition with a unit keeps a person form. A person form contains no role identifier.

From given alone. A request with phase `reachable` has no `wanted`, takes a cap of 20 by default, and rejects `not_obtainable`, `only_obtainable`, `criterion`, `work_budget` and `backend` as `unexpected_member`. Without `object` its object kind is the one kind that has every given and obtainable role, otherwise `ambiguous_object`. The answer, `ReachableAnswer`, lists the quantities reachable from the given and obtainable roles by the two-stage forward listing of `calc-core`, each with steps, rule, inputs, derivation, uses, conditions with `holds` decided from the given values, `needs_obtainable` and sources, and the exact total. A reachable line is `Outcome::Reachable` and is saved as `not_evaluated`, because session format version 2 has no outcome for it. On such a line `mark` accepts obtainable and unmarked, `set_given` keeps the phase, `set_criterion` and `find_ways` are `unexpected_member`, and `choose_wanted` sets the wanted role, phase `ways`, the object kind of the listing, and the client's criterion and cap.

The given-and-wanted form. `request_from_form` turns the rows of the form into a request: the wanted row is a role name or its name in words, a given row is an object kind or `name = value`, where the value part is read as an expression and split into value, uncertainty, coverage factor and unit, and the criterion row lists the criteria with a front flag. The request has phase `evaluate`, so a way whose inputs all have values is solved. A row error names its row, and `form_error_message` gives its words. `SolveVocabulary` is loaded for a resolved `Locale`, so `de-DE` finds the German content names, and gives object and quantity names in the form a place asks for: `NameForm::Heading` where the name begins a heading, label, list entry or table cell, and `NameForm::Running` inside a sentence or a value text. Both forms come from one locale's content, `en` when the locale has no file, and an identifier is shown only for an object or role the concept set does not know. A form row accepts the identifier, the heading form or the running form. It also gives the formula of a rule, the lists of names and identifiers, and the expressions of a bound rule as the bodies of their content lambdas from the concept set, `cockpit_criterion` is the cockpit default of fewest measurements then smallest uncertainty, and `criterion_message`, `quantity_mark_message` and `score_text` give the words of criteria, marks and way scores. `Session::record_summary` summarizes a record inside a solve answer the way `line_summary` does for an ordinary line.

Display units. `decide_display_unit` decides the unit a value is shown in and returns the unit with the step that decided it, `DecidedBy`, so a frontend opens that step's entry when the person chooses the displayed unit. The decision also carries the kind that was used, including a kind selected by dimension, and the identifier of the curriculum when a curriculum decided. `TaskContent` (a Train task value) and `CoherentOnly` (`--coherent-units`) give the coherent unit with no door. `Coherent` is the last step after nothing applied.

The readable unit pick and the reading. For a Calculate line, `displayed_line` asks this order: a unit written at the root, a unit the person set for the kind, the units written inside the expression, the list of the kind in the unit system or curriculum, and the coherent unit. A `Displayed` entry may name a list such as `mm, cm, m, km`. Among the candidates of a step, ascending by scale factor, the pick takes the largest unit in which the magnitude reaches 1, and the smallest otherwise. A value whose coherent form is an integer or a decimal may take only a unit in which its expansion terminates, so 2500 m shows as 2.5 km while 1 m with the list `in, ft, mi` stays in metres. The magnitude is compared exactly, and through an enclosure where the factor or the value carries a power of pi. The candidates written inside the expression are every written unit of the value's dimension and each of its named factors raised to its power, together with the units of the list that are the same unit under another decimal prefix; for the kind time only a unit with a terminating factor counts, and the temperature kinds take no such step.

A displayed value carries its `reading`: four significant digits of the exact value in the displayed unit, rounded with a tie away from zero as schools round, written plainly for magnitudes from 0.001 up to 1000000 and otherwise with a power-of-ten exponent, such as `138.9` or `3.333e6`. A value whose expansion ends within four digits, a machine value, a measured value and a value in a compound unit get none, and a symbolic value gets one only where its enclosure reaches four digits within the enclosure budget. The frontends draw the sign and the column.

`Session::displayed_line_summary(id, preference, coherent_only)` is the line summary of a Calculate line in its displayed unit: it asks the display order with the unit written at the root of the line's expression, a quantity literal such as `5 km` or the target of `->`, then the session override, the given preference and the coherent unit, and replaces the value, the unit, the uncertainty and the rounding bound of `line_summary` with their displayed forms. `line_summary` itself and the JSON of a line stay coherent. `Session::displayed_value(record, decision, significant_digits)` applies a display decision to a result. `DisplayedValue` holds the displayed unit in its display form, the deciding step, the converted value text, the number of significant digits when the conversion rounded, which is the requested count or the full digits of the format when none is given, the uncertainty and the rounding bound scaled into that unit and rounded upward, and the coherent value and unit from the record. A compound unit such as `h min` converts into its last part only, so `DisplayedValue` gives `90 min` and not the leading parts; showing `1 h 30 min` needs a later change that reports the parts. A value that cannot be shown in the decided unit keeps its coherent unit and says why in `kept_coherent`: an exact value whose conversion would be irrational, a conversion that does not apply, or a value that is not a real scalar. The record and the JSON output stay coherent.
`Session::displayed_value(record, decision, significant_digits, forms)` applies a display decision to a result. `DisplayedValue` holds the displayed unit in its display form, the deciding step, the converted value text, the number of significant digits when the conversion rounded, which is the requested count or the full digits of the format when none is given, the uncertainty and the rounding bound scaled into that unit and rounded upward, and the coherent value and unit from the record. A compound unit such as `h min` converts into its last part only, so `DisplayedValue` gives `90 min` and not the leading parts; showing `1 h 30 min` needs a later change that reports the parts. A value that cannot be shown in the decided unit keeps its coherent unit and says why in `kept_coherent`: an exact value whose conversion would be irrational, a conversion that does not apply, or a value that is not a real scalar. An exact rational value and coherent value are written in the form that `Session::displayed_forms(id, decision)` decides from the line's expression against the displayed unit and against the coherent unit; a value rounded by the conversion is written as its decimal, and a record without a line takes `DisplayedForms::fractions()`. The record and the JSON output stay coherent.
- The steps come in this order:
  - the unit written in the expression;
  - in Learn and Train, the unit the task, concept or exam states;
  - then the order of the area;
  - then the coherent unit.
- The area orders:
  - Calculate and Explore: the session override, the Units preference, the active curriculum's `Displayed` unit.
  - Learn: the curriculum's `Posed` unit for a given value and its `Displayed` unit for everything else, then the session override and the preference.
  - Train: a value that is task content without a stated unit is shown in its coherent unit, and a value around the task follows the Learn order.
- `coherent_only`, for `--coherent-units`, skips every step after the written unit.
- `UnitsChoice::unresolved_overrides` lists the kinds whose unit text does not resolve, so the CLI and the Units layer can report them. Whether a unit fits its kind's dimension cannot be checked yet, because kinds have no dimension table.
- The caller passes the session override only while a session is current.
- A step names units by quantity kind, and applies when its unit passes `check_kind_unit` for the kind and is of the value's dimension. A step that does not apply is not applied, and the next step decides.
- A value without a kind, such as a Calculate line, takes the unit of a step only when that kind's dimension determines it and exactly one kind declared in that step has a unit of the value's dimension. Otherwise it keeps the unit it was computed with, so `2 N * 3 m` reads `6 N·m` and never `6 J`.
- `UnitsChoice` is the Units preference and the session override alike: a unit system and unit texts per kind, as the session file stores them. A kind override wins over the system's unit for that kind. `UnitsChoice::from_settings` reads the system and `kind=unit` entries that the CLI flags `--units` and `--unit` and the cockpit's Units layer give, with a typed `UnitsChoiceError` naming the entry.
- `resolve_display_unit` reads a unit expression, a compound such as `h min` (parts separated by whitespace), or a scale name such as `celsius`.
- Unit systems and curriculum units are passed in as `UnitSystem` and `CurriculumUnits`, because no content and no loader for them exist yet.

The language reference. `localized_language_reference` is the command both frontends call: it takes the typed reference `calc-syntax` generates and groups its entries in a fixed order, each group with the message key of its heading and each entry with the two message keys of its construct, or none when a construct has no words, so an entry is never dropped silently, the name and the sentence on what it means. It renders nothing, so a frontend shows the words of its locale and the CLI's JSON output carries the keys instead. `Message::key` of `calc-i18n` names a key for JSON output. `construct_words` gives the two keys of one construct and `reference_group_message` the heading of one group. `language_reference_json` writes the whole reference as canonical JSON: the groups with their heading keys, each entry with its construct, its two message keys, its spellings with their placeholders, its canonical forms, its precedence and its arguments, then the precedence table, the unit table with dimension exponents and exact scale factors, and the decimal prefixes. A construct the reference does not hold has no words, and a test over the generated reference fails when a construct has no keys or a key is empty in a shipped locale, so the language cannot grow without its words.

The working's rules. A solve line's working carries the rule chain of its derivation, recomputed by running the request again and never read from the stored answer. Each `WorkingRule` holds the way identifier, the output and input roles, the value of every input and the rule's result with its reading, the conditions with their three-valued `holds` and whether the given values could have failed them, the source identifiers, and the blocks the concept rests on, which travel with the rule for the rigorous version and are never shown unless a person asks. `rendered_rule` turns one rule into the person form with a `SolveVocabulary` and a symbol map: the roles in their running form, the formula, the formula with the values in place of the names where every input has one and nothing at all where one is missing, and the result, so a frontend shows `U = π · d`, `π · 5 cm` and `5 · π cm` with the reading `15.71 cm`. Values are written in the unit the request wrote for that dimension, else in the coherent unit. The steps under the chain are the arithmetic of the derivation with the given values in place, so a solve line has both parts, the rules and the arithmetic. JSON carries the identifiers, values, conditions and sources, and no rendered words.

The working view. `ResultView::Working { path }` is the fourth view, run as a `ViewJob` off the session thread like the others, and `AvailableViews::working` says when a line offers it: an expression line with a result whose input holds an operation. The job takes the line's own expression, copied into its own pool through its printed text, and the values of the lines it refers to, so a reference is a step of its own and its own working is a request for that line. An exact line is worked exactly; a machine line is re-run on the backend its record names, taken from `registered_backends`, in the domain of its stored value. `WorkingOutcome` is either the steps with `further_steps` and `further_paths`, or a `WorkingRefusal`: `BackendUnavailable` when the record's backend is not registered here, `ApproximateOperations` when its plan holds an approximate operation, and `ResultDiffers` when the recomputed root does not give the value the line holds. A step's operator is the construct of the language reference, so a frontend renders its words through `construct_words`, and `working_operation_message` and `working_refusal_message` give the words for one operation and one refusal. `view_outcome_json` writes the steps with their paths, operands, results and formats, the operator as its construct, and no rendered words.

Recognition. A line's concepts are recognized after its value, never before it: evaluating a line puts it in `pending_recognition`, and a frontend turns each pending line into a `RecognitionJob` with `Session::recognition_job` and steps it off the session thread, so a result is reported without waiting. A line with a value is matched by the concept matcher over its written expression, with the patterns of the loaded concept set built in the job's own pool and the matcher's limits; a solve line is not matched at all but named by the concepts of the rules of its canonical derivation, in derivation order and with no coverage and no bindings; a line that is not evaluated, failed, defines a function or holds a picture has no job. `Session::apply_recognition` takes the job's event: an answer of an older generation is dropped, and a current one stores the matches in the line's record, the concept set version as sixteen hex digits, the site and each binding printed in ASCII under the pattern's own variable name, and the three-valued `holds` of each condition. `Session::run_pending_recognition` runs everything queued to completion on the calling thread, which is what a one-shot CLI run does before it answers, and `Session::start_pending_recognition` hands the same work over as jobs for a frontend with a worker, which is what the cockpit does after every evaluation. `Session::recognition_state` says `running`, `ready` or `unavailable` with its reason, and a line that is queued and not yet taken reads as `running` too, so the interval between a value and its recognition is never silence, so a line whose recognition has not finished never reads as a line with nothing recognized. A frontend reads the answer as one `RecognitionSummary` of five: not run, running, matched, nothing matched, and a search cut short before anything matched. A matched offer carries the identifiers of the concepts the loaded set holds, the count of the matches it does not hold, and the record's `truncated` and `truncated_by`, so a frontend names what this version knows and counts the rest without counting by subtraction; where the concept set could not be read at all the count is absent rather than zero, since nothing about those matches can be said. Editing, renaming or recomputing a line raises its generation and puts it back in the pending list; `cancel_recognition` drops a running one, and a cancelled job sends nothing.

The concept command. `concept(identifier, lens, origin, locale)` returns one concept of the loaded set: its identifier, the lens it was asked for or Explore where none was, the lenses that have something to show, the line it was recognized in when there was one, its text with the locale those words are in beside it, the asked locale where the content has it and English where it does not, so a reader is told which language the words are in rather than being left to assume the one asked for; a concept with no text in any locale has no wording at all rather than a made-up one, which the loader's rule that every concept carries English text keeps out of a loaded set, its level, its prerequisites, its sources and its exercises. A lens shows something when the content gives it something: Explore when the concept has a way or a bound, Learn when its text has an intuition, examples or a misconception, Train when it has exercises, Read when it has sources. A lens with nothing to show is not an error: the outcome names it as asked and leaves it out of the list. Learn is decided on the text in the locale the outcome carries, so the list is answered per language and a caller asks again when the language changes rather than keeping the one it had. The first argument is what the person asked for: an identifier, or a concept's name as this locale shows it, because the row a person reads names concepts and never identifies them. An identifier is matched first and exactly; a name is matched after it, trimmed and without regard to capitals, against the name the same locale would print. A name that two concepts carry is the typed `ConceptError::AmbiguousName`, which names both identifiers, since the name is what is ambiguous and the identifier is the only thing left to choose by. A wanted concept that is neither is the typed `ConceptError::UnknownConcept`, which names it, and `concept_error_message` gives the words. The command stores nothing: where Back returns to is the navigation state and not this outcome's.

Preferences. `PreferenceStore` keeps the device preferences: language, theme, text size and units.
- **Storage:** the store goes through the `Storage` part of the platform boundary, `NativeStorage` for files (it creates a missing parent directory, writes a temporary file named with the process id and renames it, and removes the temporary file when the rename fails) and `MemoryStorage` for tests.
- **Location:** the frontend passes the location. `None` keeps preferences in memory only.
- **Opening:** `open` reads once and reports `PreferenceEvent::Opened` with the preferences and a `StoreState`:
  - `Missing` and `Unreadable` (not JSON, another format, no valid version) give all defaults.
  - A member of the wrong type or with an unknown value takes its default, and unknown members are ignored.
  - A higher version is `Newer`: its known members are read, and opening writes nothing.
- **Setting:** `set` changes one preference in memory at once, then reads the file again, applies only that member to what it read (or to the in-memory preferences when the file is missing or unreadable), and writes the whole file in version 1. Writes are serialized, and a failed write keeps the change in memory and reports `PreferenceEvent::Written` with the `StorageError`.
- **File form:** the canonical JSON with `format`, `version`, `language`, `theme`, `text_size_percent` and `units`, the unit overrides sorted by kind. An empty units choice is stored as `null`.

Which instruments apply. `applying_instruments` takes a line's outcome and the two facts only a frontend holds, whether `calc-viz` can draw the line and whether the frontend's own row had to shorten the naming, and gives the instruments that apply in this order: Inspect, Method, Plot. Inspect applies to every line but a definition, where it applies only when the naming was shortened; Method to a line the person asked a way or a reachability of; Plot when a scene exists. The three further instrument names with nothing behind them yet, Data, Verify and Export, are not in the list, because an instrument nothing can produce is a tab nobody can open. A frontend with no rows, such as the CLI, passes `naming_shortened: false`, which is true of it: it shortens nothing.

The one search. `SearchEntry::ALL` is what the search can find: the two session settings, the four preferences, one entry per keyboard zone for a keyboard without a function row, cancelling a running line, and the unit of a picture axis. Each gives its name and its everyday words as messages, and each says from which context it can be reached, so an entry whose control cannot be reached from here is not listed. `search` takes a query, a `SearchContext` and a locale, and gives the matching entries and, below them, the answer pointers; it finds nothing during an exam. Beside those it gives one hit per construct of the language reference, matched by the construct's spellings as well as by its two message keys, so `\u{3a3}`, `\u{221a}` and `sum` all reach the same entry; each hit carries the construct and its name in the locale, and they are listed after the entries and the answers, since there are far more of them.

The application place.
- **Pointers:** `Pointer::ALL` is the closed list of pointers in a fixed order. Each pointer gives its name, everyday words and sentence as messages, and a door pointer its `PointerDoor`, whose message names where it leads. `pointer_block` gives the block for a `PlaceContext`: every pointer, the doors to the session bar and its menu only while a session is current, and nothing in the exam layer. `search_answers` gives the answer pointers, the only ones the search shows.
- **Unit systems:** `shipped_unit_systems` lists the content unit systems in file name order, each with its name in the locale (English, then the identifier, when the locale has none) and its displayed unit text per kind. `override_kinds` gives the kinds that a shipped system declares, ordered by their name in the locale, as rows of the Units layer.
- **Per-kind check:** `check_kind_unit` checks a unit text for one kind with the loader's own check in `calc-concepts` and returns the text with its parts separated by one space. It refuses a text that is no unit, a unit of another dimension, a compound for a kind other than time, length and mass, a compound whose parts do not descend, a unit in place of a scale for a temperature reading, and a scale for any other kind, so a temperature difference is never shown through an affine map. A text the loader accepts but the display cannot show, such as `1` for a count, is refused as not a display unit. `kind_unit_problem_message` names the problem in words. The preference, the session override and the display decision use the same check.

The session unit override.
- **Commands:** `Session::set_unit_override` stores an override after checking its structure: not empty, identifiers for the system and kinds, kinds in byte order without repeats, and no empty unit. A failure is a typed `UnitOverrideError` and changes nothing. `clear_unit_override` removes it.
- **Validation:** the override is validated against the content once, when it is set, cleared or opened, and `applied_unit_override` reads the stored result. A system that no content unit system has, a kind that is not a quantity kind, and a unit that does not resolve or does not have its kind's dimension are left out of the applied `UnitsChoice` and listed as `OverrideProblem`s. They stay stored unchanged, so saving keeps them.
- **Messages:** `override_problem_message` gives the en and de message that names what was not found. A unit whose kind is known names the kind in words through `quantity_kind_message`. Only an unknown kind is shown as stored.
- **Display unit:** `Session::display_unit` decides the displayed unit in the display order, with the stored applied override as the session override and the content unit systems, read once when the session is created or opened.

JSON reading and writing are in-house, without a crate. Integers are written as decimal digits of any length, and times as `YYYY-MM-DDTHH:MM:SS.mmmZ`.

Pictures. `Session::plot` takes a `PlotRequest`: the line, optional view states (one `ViewState` per view, each axis an optional exact interval and a display unit, and a camera for a space view), divisions per axis of every view, and free parameter values by name. Without view states it uses the line's stored `picture`, and without that the default view. It expands the line's references like evaluation does, but leaves names that no line defines free. Those free variables, in order of first use, minus the variables given a value as parameters (in the request or the stored picture), are the axis variables, and the count picks the primitive: one axis variable is a curve in a plane view, or a complex grid over its complex plane when the expression contains `i`; two are a scalar grid in a plane view, or a surface when the view state has a camera; none, a space view for one variable, a complex value of two, or more than two are the typed errors `NotPlottable`, `ViewKindMismatch`, `ValueKindNotPlottable` and `TooManyAxisVariables`. An axis without an interval samples −10 to 10, 0 to 100 for a temperature axis, and −2 to 2 for each axis of a complex grid; a value axis without an interval is left to `calc-viz`. A function naming line is plotted over its own parameters, and a free variable of its body that is not one of them is a free parameter like any other: `psi(x) = sqrt(2)*sin(n*pi*x)` with `n` given plots over `x`, as the same expression without the head does. A parameter naming nothing free in the plotted expression is `UnknownParameter`, and giving every variable a value is `NoAxisLeft`, which says so rather than reporting the line as not plottable. `plot` also checks the view and axis counts, each display unit against its axis's dimension, empty intervals, unknown parameters and missing divisions. An axis variable has no dimension of its own, so an input axis takes the dimension of the unit it is shown in: `x * 1 m/s` over an axis in seconds is a length, and the value axis then takes metres, or any unit of that dimension. The value's dimension is read from the expression with each axis variable replaced by one of its axis's unit, so the substitution that gives the axis its dimension is the one the value is measured by, and an axis left coherent stays dimensionless as before. An axis whose dimension names one quantity kind on its own (`dimension_determines_it`: length, area, volume, mass, time, speed and force, but not energy or temperature, which share a dimension with another kind) is titled by that kind's word from calc-i18n rather than by the variable name or the line label, so `x * 1 m/s` over an axis in seconds reads `time in s` and `length in m`. A line the person named keeps its own name on the value axis, and an axis whose dimension names nothing keeps what it had, which is what a picture of an expression written without units shows. `Session::axis_titles` gives the titles for the view states a caller is about to plot with, because a display unit given at the command line is not in the stored or default views. An axis unit that makes the expression inhomogeneous, such as a bare number compared with the axis variable, is refused with the dimension fault instead of being drawn. `Session::picture_defaults` gives the stored or default view states, the axis names and the legend before sampling, so a frontend knows the plot area first, and `Session::is_plottable` says whether a line has a picture. `exact_number` reads an exact coordinate typed in the input language, and `plot_json` writes the path, the image size, the view states and each layer's precision limit of a written picture. The sampling precision is `f32` under the `f32` setting and `f64` otherwise, with the session's backend preference. `plot` prepares the sampling on the calling thread and returns a `PlotJob`. The job implements `Job` of the platform boundary: each `step` samples up to 4096 positions, and it sends two completions over the channel given to `plot`. `PictureEvent::Samples` comes first, with the scene of the samples, without bounds and in the provisional style, which cannot be read from. After it, the job encloses the samples in steps of up to 512 positions, and the last step sends `PictureEvent::Bounds` with the settled scene. A sampling error sends `Failed`. A `Failed` after a `Samples` of the same generation replaces it, so the receiver removes the provisional picture instead of keeping it. A `PlotRequest` also names a `PictureSlot`, the place the picture is shown in: the inline picture, the Plot instrument, a detached window, or one CLI invocation. The frontend chooses the number and keeps it while the place exists; a slot is never saved and no record names it. A newer plot of the same line and slot stops the job in either stage by setting its cancellation flag, and nothing more is sent after the flag is seen. A plot of another slot of the same line, or of another line, cancels nothing. A cancelled job finishes at its next step and sends nothing. A job on a worker can still send once after a newer plot set its flag, because it checks the flag before sending and the flag may change in between, and no lock is held across a send. `Session::cancel_plot` ends a slot whose place goes away, such as a closed card, a changed instrument tab or a closed window: it sets the running job's flag and drops the slot's latest generation, as `cancel_view` does for a result view. Every `PictureEvent` names its line, its slot and its generation, and the receiver drops every event whose generation is not `Session::latest_picture_generation` for that line and slot, which is what makes the latest request win. A function naming line `f(x) = …` is plotted over its parameters in order: its lambda chain is opened with `calc_expr::open_lambda_chain`. A call of a function naming line, such as `g(t)` after `g(x) = x^2`, is inlined with `calc_expr::apply_lambda` before sampling, so the sampled variables are the free variables of the inlined expression and a called function's head is never one of them. A solve line is not plottable, and a line number beyond `u32` has no `ResultId`. `Session::settle_picture` writes what a frontend settled on into the line's `picture` member: it takes one view state per view and the parameter values, checks them against the line's scene as `plot` does, refuses a view axis without a range, and evaluates nothing. `Session::read` and `Session::commit_reading` take a reading of a picture. Both name the line, the slot, the generation of the complete scene shown, the layer and one coordinate per input variable of that layer. A coordinate is a pointer value, which is converted exactly and snapped to the decimal with the fewest significant digits within half a step of the axis shown, ties to the even last digit (`snapped_coordinate`), or a typed exact value, which is taken as it stands. A generation that is not the latest finished scene of that line and slot, a layer that offers no readings, and a coordinate count that does not match are the typed errors `SceneNotComplete`, `LayerHasNoReadings` and `CoordinateCount`. A transient `read` returns a `ReadJob`, which evaluates the plotted expression at the coordinates on the executor and sends `ReadEvent::ReadingFinished` with the record or `ReadingFailed` with its diagnostic, changing nothing in the session; a newer transient read of the same line and slot cancels the older one. `commit_reading` enters the call of the source line's function at the snapped or typed coordinates, such as `f(0.5)`, and keeps the picture it was read from in the new line's `reading` member: the source line, the view with its display units, the divisions, the coordinates and whether they were snapped. A source line that is not a function naming line is `ReadingNeedsFunctionForm`, and a reading that cannot be built from the picture at all is `ReadingNotBuilt`. A picture stays readable while a newer plot of the same line and slot is still sampling: the last finished scene and its plan are kept for the place until a newer generation finishes, which is the ordinary case of a person reading the picture they can see while a zoom is still being drawn. `Session::cancel_plot` drops both and cancels the slot's transient reading as well, and `Session::cancel_read` cancels only the reading.

Escape-time pictures. A line whose input text is `escape_time ` followed by a request in canonical one-line JSON is an escape-time line: `form` is `quadratic_parameter` or `quadratic_initial`, and `c` with exact `real` and `imaginary` values belongs to `quadratic_initial` alone. An invalid request is refused with the member that is wrong, as for a solve line. Such a line has no value: its outcome is `Outcome::Picture`, its summary state is `LineState::Picture`, and editing its text changes the form or the centre. `Session::escape_time_line_of` gives the request back. `plot` of such a line takes `iteration_limit` instead of parameters, and refuses a parameter value on an escape-time line and an iteration limit on any other line. Without a limit it uses the line's stored one and then the default limits, and without a view state the default view of the form. On the session thread it does only the pool work, lowering the map to an execution plan through `calc_viz::plan_refinement`; the job then builds the levels, which needs no pool, and samples them. Each coarser level arrives as `PictureEvent::Samples` with a complete scene put into the provisional style without bounds, and the finest level, the scene of the full request, arrives only as `PictureEvent::Bounds`. Measured in a release build, `plot` held the session thread 0.26 to 0.61 ms at 1920 by 1080 cells and 0.25 to 0.28 ms at 7680 by 4320, inside the 50 ms the session thread may be held and not growing with the image.

`settle_picture` of an escape-time line takes `iteration_limit` beside the settled view and writes both, and refuses a parameter value; of any other line it refuses an iteration limit. `read` of an escape-time line snaps the point as for any picture and then reads the orbit through `calc_viz::read_orbit` with the limit of the scene it was read from, sending `ReadEvent::OrbitRead` with the class, the escape count when the point escaped, and the limit used. A committed reading enters a line whose input text is `escape_time_reading ` followed by canonical one-line JSON with `form`, `c` for the initial form, `at` and `limit`; that line evaluates the map at `at` with exactly that limit, so its result depends on no view or rule, and its outcome is `Outcome::EscapeTimeReading` with the orbit, written as the status `escape_time_reading` with `class`, `count` and `limit`. `Session::orbit_json` writes one orbit for a frontend. An escape-time line and a reading line are recognised again when a session is opened, as a solve line is.

The session format is version 8. The `picture` member gains `iteration_limit`, `null` for every line that is not an escape-time line and for one that uses the default limits, `{"rule": "fixed", "iterations": n}` or `{"rule": "following_depth", "base": b, "per_halving": p, "cap": c}` otherwise, each value within its allowed range. A version 7 file converts by adding `iteration_limit` `null` to every `picture`, so such pictures reopen with the defaults. The outcome status `picture` is written and read for an escape-time line.

`pan_range` and `zoom_range` turn a gesture, given as machine numbers, into a new exact range: the input is converted exactly, the new bounds are computed in exact arithmetic, and `settle_gesture_range` rounds each bound to the nearest multiple of the largest power of two not above the width divided by 2^32, ties to even. A range without positive width, a non-finite input or a non-positive zoom factor gives `None`, and the caller keeps the previous view.

Reading and writing files and the session executor are not part of this crate yet. Sessions are opened from and saved to bytes, evaluation runs on the calling thread, and plot jobs are stepped by the caller.

Result views. `Session::available_views` says which of `digits`, `enclose` and `machine-line` apply to a line. `Session::view` checks the line and the limit (78913 places, 1 to 5000 significant digits) and returns a `ViewJob` that runs off the session thread and sends one `ViewEvent`: `digits` truncates an exact rational or finite machine value with its remainder and period (`of` names which), and `enclose` encloses the true value of the line's expanded expression, copied into the job's own pool through its printed text. A newer view of the same kind on the same line sets the cancellation flag of the older job. A job on a worker checks the flag before sending, so it can still send once after a newer view started; the receiver therefore drops every `ViewEvent` whose generation is not `Session::latest_view_generation` for its line and kind, as for `PictureEvent`. A job does its whole view in one `step`, and an enclosure at 5000 digits can take seconds with cancellation checked inside the refinement, so a frontend steps view jobs off its UI thread. A view is recomputed each time and never stored. `view_outcome_json` writes an outcome with the members of its view. `Session::machine_line` enters `to_f64(<name or label>)` or `to_f32(…)` as an ordinary dependent line, and fails with `MachineLineNotApplicable` for a function definition, a solve line or a line without a result. `view_error_message` gives the words of a view error.

Shape matching. `ShapeMatching::new` deals a round of an activity: one house per listed shape, upright, and one piece per shape, in an order in which no piece starts at its own house, which round `k` takes as the `k`-th such order, so rounds differ without a random generator. A piece of `orientation` is turned where the turn shows, 45° for a square and 60° for a triangle, the angles farthest from every multiple of 90° and 120°, and a circle is not turned; a piece of `size` is at half its house's size, which is chosen, and is wrong if children who match at this level do not see the difference or fail at it where a smaller difference works. `place` moves a piece into a house only where `fits` holds, the house of its own shape, and otherwise answers that it went back; nothing about a round is kept or counted. `concept_activities` gives a concept's activities and `beginnings_with_activities` the declared beginnings that hold any, for a Learn landing, and the Learn lens counts a concept's activities as something to show.

A line holding a `chem'…'` substance answers its composition, and one holding a reaction answers its balance with the count of each element and the charge on each side, or a refusal that says why there is none. A substance or reaction used as a number is refused with the property to ask for. A molar mass answers through the worst case with notes naming CIAAW 2024, CODATA 2022 and which elements' ends are natural intervals or expanded uncertainties, and records both tables as method parameters.

A line holding a `nuc'…'` nuclide answers its A, Z and N and whether AME2020 holds a measured mass for it. A nuclear reaction is checked as written and answers its mass number, charge and electron lepton number on each side, or names the first that fails, the neutrino that would balance a failing lepton number, and the only balance where the kernel has one. A Q value answers through the worst case in keV, with notes naming AME2020, CODATA 2022 and the coverage, the atomic-mass convention, an electron capture or a positron, and for a decay whether its sign rules it out for the neutral atom or is not decided; the tables and the coverage factor are method parameters.

`solve_ode` reads an initial value problem as the command line gives it: equations `diff(x, t) = …` separated by semicolons, `--initial` assignments of the time and each name, and `--at` times as `t = 1, 2`. Each name keeps the unit its initial value was written in, and the time the unit of the start. Every name and the time on a right side are replaced by the quantity of that name in its unit, and the side is divided by the unit of x per unit of t; where the units fit the result is dimensionless, and its coherent form is dx/dt in the written units, so the integration and the answers run in the units the person wrote. A right side whose unit does not fit is refused naming the unit it has and the unit it needs. Initial values are enclosed from 20 significant digits, times must be exact rationals, and a unit with an offset (°C) is refused. The report gives, per requested time, each component's enclosure rounded outward to the digits its width supports, its width (the interval bound), and per component the largest per-step remainder (the step bound); `ode_report_json` writes it with `step_bound` and `interval_bound` named as such.

`cargo test -p calc-app`
